# Experimental SteamVR server backend

This Windows x64 backend changes control sources inside `vrserver.exe` using its driver interface methods. It registers no HMD, controller, tracker, display component, or virtual display. The connected vendor HMD continues to own rendering and its stereo display. The connected Virtual Desktop route has limited live and human evidence in the project reports; each newer candidate still requires runtime validation. The installed build is an experiment allowlist, not a compatibility certification.

## Activation and exact gate

The package does not register the driver or start/restart SteamVR automatically. After explicitly opting in and registering it while SteamVR is stopped, the companion driver can load at the next normal runtime start. Its sole configuration authority is the explicit current-process-token Windows `FOLDERID_Profile` known folder followed by `VRC-SWITCHEROONIE\config\driver.json`. There is no legacy AppData fallback or automatic migration. Mutable environment variables and the runtime working directory cannot redirect this opt-in file:

```json
{"experimentalOptIn":true,"approvedRuntimeBuild":"25330290"}
```

Only runtime buildid `25330290` is currently admitted by the compiled gate. The exact value is read from `appmanifest_250820.acf` above the actual running `vrserver.exe`, never inferred from an SDK version. The two interfaces must exactly be `IVRServerDriverHost_006` and `IVRDriverInput_004`. Any missing build manifest, different build, absent interface, disabled opt-in, unknown existing method detour, or unexpected module implementation prevents routing. The driver reports the reason through IPC and SteamVR's driver log.

Startup configuration uses a bounded Win32 file read, admitting at most4096bytes and rejecting an incomplete/changing size. Read/delete sharing permits atomic replacement but prevents concurrent in-place writers from tearing a same-length snapshot. UTF8 BOM is accepted; the exact two-key schema remains strict. Numeric startup diagnostics report resolution/open/read/schema stage, system error, and byte count without paths or account identifiers. Error10 distinguishes resolution/read/size failures; readable malformed schema remains Error4. This diagnostic repair does not itself prove the cause of a prior runtime-only startup failure.

The default manifest's `alwaysActivate` loads this companion after registration even without its own devices; it is not a fake HMD presence claim. An empty HMD-presence list creates no display path. Scenario C (absent headset launch, attach later) remains unimplemented.

The package ships `resources/settings/default.vrsettings` with only `driver_switcheroonie.loadPriority=20000`. [Valve's pinned driver documentation](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/docs/Driver_API_Documentation.md#resourcessettingsdefaultvrsettings) specifies that higher priorities load first and that `steamvr.vrsettings` overrides driver defaults. The observed installations use Virtual Desktop priority 1000 and SpaceCalibrator priority 9999. This companion must initialize before the vendor creates input components so its creation hooks can retain their handles. Changing external-driver registration order does not establish that ordering. Existing user priority overrides and vendors with priorities at or above 20000 require inspection. An observed startup nevertheless initialized Virtual Desktop before higher-priority SpaceCalibrator, so priority alone has not proven the required early initialization phase. The next runtime-start log and captured-component capabilities must confirm actual ordering. This file changes only this companion's defaults; no vendor settings are edited.

## Provenance and routing

Input creation hooks install during provider initialization. Pose-hook installation is deferred to `RunFrame`, allowing other companion providers to initialize; the unpatched direct runtime route waits three seconds. For the approved SpaceCalibrator route below, it intercepts the verified original pose trampoline instead of overwriting SpaceCalibrator's runtime method entry. The `DriverPose_t` argument is atomically captured before synthetic output is passed onward. It is calibrated physical data when SpaceCalibrator is active. Client `GetDeviceToAbsoluteTrackingPose` results are never used as independent physical evidence.

Ordinary desktop synthesis selects active HMD index0 and devices whose actual properties say `Controller` plus `LeftHand`/`RightHand`. Role properties are hints: if multiple devices compete for either role, that hand's synthesis is refused rather than guessing which device SteamVR selected. Generic trackers pass through unless the separately enabled, leased body-spin transform below is active. That transform permits only identity-verified HMD, Controller and GenericTracker classes; tracking references and display-only devices are always excluded. Eye tracking and haptics pass through. No serial, role, universe, calibration property, vendor setting, or binding is changed. Physical FBT and application IK behavior still require testing.

Head/controller source roles also require complete bounded tracking-system, serial, and model properties. The owned research display is excluded by tracking-system `switcheroonie_persistent_synthetic`, serial prefix `switcheroonie-persistent-`, or model prefix `Switcheroonie Persistent ` (ASCII case-insensitive). Its synthetic pose or proximity cannot establish physical readiness. These identities are inspected only in memory and never logged. If a transport replaces every identity field, the property filter alone cannot establish provenance; an independently measured physical bridge is required before admitting that research route.

On each successfully committed desktop transaction epoch, an immutable anchor is captured from the physical head. Its world-space position and yaw are retained, while physical pitch/roll are removed. Temporary invalid/stale command or physical-stream fallback does not erase that epoch's anchor; fresh recovery in the same epoch retains its position and orientation. A later desktop epoch captures a new anchor once. Desktop height modifies global Y. Yaw and pitch fields are accumulated offsets in radians, with positive yaw looking right and positive pitch looking up. Hand presets0/1 use near-hip positions and level raw wrist rotations, independent of head pitch; preset2 provides a right pointer, and preset3 persistently raises the left menu wrist while retaining that right pointer. Right use/grab can also extend the active interaction hand. These poses use the observed raw binding convention, with no production Quest2 tip-angle correction or claim of actual avatar palm/IK appearance. Synthetic derivatives are zeroed. Physical return passes the newest vendor pose unchanged unless an independent body-spin lease remains active.

Both the broker heartbeat and connected physical head stream must remain fresh within200ms for desktop synthesis. Missing/invalid data returns physical passthrough and neutralizes owned actions; headset sleep or stream termination is not claimed to preserve the scene. The last complete command may be used across a brief odd IPC publication, but only until its original timestamp expires. Armed=false retains the desktop head anchor while returning wrists to rest and neutralizing actions/posture.

Body spin is an additive pose transform in either Physical or Desktop mode. The broker must explicitly enable it and publish a separate fresh200ms lease, a finite normalized WORLD quaternion, a bounded finite WORLD pivot and a nonzero generation. Native additionally requires a current accepted epoch and a valid, identity-approved independent physical HMD source within200ms; fresh controllers/trackers cannot continue a partial spin after head tracking expires. The broker retains the same pivot throughout a spin generation; it may derive a relative hip center from the independently captured head, without assuming the application's floor. Native applies the quaternion after ordinary pose selection: `qWorld'=qSpin*qWorld` and `tWorld'=pivot+qSpin*(tWorld-pivot)`. All eligible head, controller and body-tracker outputs therefore rotate together, preserving inter-device distances and the original driver-local pose/head offsets. Independent physical captures, calibration input and reported physical WORLD head coordinates stay unmodified. Changing eligibility/container, head permission and epoch are rechecked before returning an output. Spin does not require desktop pointer arming; its lease has independent explicit ownership.

Previously transformed devices are restored through their captured vendor host contexts when the lease expires, is released, or becomes invalid, including generic trackers during Physical mode and without waiting for another vendor callback. A stale source is restored with an invalid tracking flag rather than falsely reporting it fresh. References are never transformed. The imposed changing quaternion is sampled pose geometry; its additional angular/linear prediction derivatives are not synthesized. This does not set a private avatar root/animation state, guarantee cartwheel IK or FBT compatibility, or create a missing physical/display transport. Human application tests remain required.

Real-time callbacks allocate nothing, perform no file/network I/O, and never wait on mutexes. State publication uses lock-free 64-bit atomics, bounded seqlock reads, and bounded try-gates. An established desktop session has no shared state lock that could leak a physical pose or button during concurrent input/status callbacks.

## Input mapping and limits

The input hooks capture boolean/scalar/skeleton/pose-component creation and retain the original existing device/container identity. Selected hand input is suppressed during desktop mode. Synthesized controls use exact component paths matching the locally observed VRChat layouts: left stick X/Y for movement, right trigger value/click for use, right grip/squeeze value/force/click for grab, right A click for jump, and left stick click for run. A menu pulse selects one captured Boolean click handle, preferring left Y, then left B, right B, and left application-menu. Other menu aliases remain zero so one pulse does not activate several bound channels. Touch components are neutral and do not impersonate click/value components or activate gesture menus. A hand preset changes pose only. Reserved `system` is neutral and is never synthesized as a VRChat menu. OSC routing in the broker must zero the native locomotion/jump/run fields to prevent duplicate ownership.

Frame submissions retain the runtime's provider context: each device uses the host `self` captured from its original pose callback, and each input handle uses the `self` from successful component creation. The companion's own interface instance is used only to identify method targets. A property role alone cannot authorize a submission before its first physical callback. This avoids the observed runtime rejection when a companion host attempted to write devices owned by the vendor.

These are component-path mappings, not proof that an application's current binding uses those controls. The path selection is still binding-dependent. Skeleton updates are held at their previous shape during desktop mode, not regenerated as a tested open-hand skeleton. Controller pose-component offsets are held. A hand-pointer's projection, vendor grip/aim offsets, menu behavior, finger animation, and compatibility with custom bindings require the real controlled test scene and per-route application tests.

Creation callbacks that occurred before this companion installed its hooks cannot be recovered through the published input interface. Missing captured components yield status `UnmappedControllers`; driver load order must be validated, and this backend cannot claim an input capability from pose detection alone. On physical return, owned scalar/buttons remain zero until the corresponding physical input is released once, preventing a held physical control from inheriting synthetic action ownership.

Unknown patched targets fail closed. One experimental local SpaceCalibrator binary is admitted only at `<SteamVR parent>/01spacecalibrator/bin/win64/driver_01spacecalibrator.dll`, with SHA256 `17b8510ee9cfc3cd017deb5a40ab6ef2ac5e5e1412f0f00038788fa6b0898314`. This exact local hash is an allowlist, not a publisher signature or a reproduced source build. `approved-companion.json` records the observed version and reviewed source comparison.

The accepted runtime shape must be a MinHook x64 relative jump through an absolute relay to this exact module. A bounded HDE64 instruction walk inside its registered x64 unwind-function range resolves the RIP-relative original pose pointer. The candidate must be executable private memory with a verified jump back to the exact runtime pose method plus5–32bytes. Ambiguous or different shapes are refused. Routing hooks that original trampoline after SpaceCalibrator has stored its raw physical shared-memory feed and applied calibration. Synthetic head/hands and the optional body transform therefore do not feed back into its physical calibration samples. Unspun generic trackers continue through the calibrated physical pipeline.

A raw passthrough guard counts the complete approved SpaceCalibrator pose call without altering its input. Public frame ticks, direct submissions, and integrity reads also participate in that lifetime count. Its provider Cleanup is guarded so shutdown gates new raw-body calls/ticks/submissions, drains existing calls, neutralizes input through a private shutdown path while trampolines remain live, restores the inner trampoline and own input hooks, then lets SpaceCalibrator free its original trampoline. A stopped outer lifetime gate and both relevant modules are retained until process exit for queued entries; this is intentionally a shutdown-only state. Normal own removal while the companion remains alive restores all own hooks and leaves SpaceCalibrator's original runtime hook intact. Failed disable/removal transactions retain stopped state and live trampolines. If an unknown add-on changes any owned method later, synthesis is disabled and module/state is pinned; the foreign replacement is never overwritten. Real headset switching, continuous calibration stability, and compatibility with other binary hashes still require hardware evidence.

## Shared memory

`Local\VRC-SWITCHEROONIE-{current user SID}` is 4096 bytes. Creation uses a protected DACL for the current user and SYSTEM. The broker owns the 512-byte request at offset 0; the driver alone owns the 512-byte status at offset 2048. All fields are published/read as aligned atomic 64-bit words under odd/even sequence counters. `protocol.hpp` supplies precise offsets; both processes share QPC frequency.

Request epochs are monotonic mode transactions, independent from input heartbeats; restart must seed the epoch from current QPC, and an existing map must retain its sequence. Old epochs are rejected. `armed` owns desktop actions/posture/hand presets; it does not authorize the separate body-spin lease. Status at offset60 contains capability bits:1 pose hook,2 input hooks,4 left move component,8 right trigger,16 menu component,32 HMD proximity,64 rigid tracked-body spin routing. These report available paths/captured components, not hardware-verified usability.

The request still uses version1 and512bytes. Preset3 at offset80 means LeftMenuNavigation. OSC owns offsets104–135. The additive spin extension uses136 active(u32),140 reserved-zero(u32),144 leaseQpc(i64),152/160/168/176 WORLD quaternionWXYZ(double),184/192/200 pivotXYZ(double),208 generation(u64). Old zero-filled extensions are inactive. Active quaternion squared-norm tolerance is1e-6; pivot magnitude is bounded10000 per axis. Its own lease and the original broker timestamp both must be fresh; a malformed active extension fails closed. Status adds288 active(u32),292 reserved(u32),296 last submitted generation(u64) and304 total body-spin submissions(u64). Active means a valid current lease matches an actually submitted generation. Physical head WORLD position remains64/72/80; consumers should never use transformed client poses as independent source/pivot evidence.

An additive status extension retains the version and512-byte block size: offset136 `anchorEpoch`(u64);144 `syntheticHeadValid`(u32);152 `syntheticHeadEpoch`(u64);160/168/176 forwarded WORLD XYZ(double);184/192/200/208 forwarded WORLD WXYZ quaternion(double);216 `syntheticHeadQpc`(i64). The snapshot records an actually forwarded head pose independently of the captured physical snapshot. `ackEpoch` reports the accepted request, whereas `anchorEpoch` reports successful desktop anchor capture. Forwarded validity requires a current request epoch, valid pose,200ms freshness, and either committed Desktop or an actually submitted current body-spin lease. Desktop additionally requires matching anchorEpoch. Consumers also check status heartbeat and pose-hook capability. Driver WORLD and client standing coordinates can differ.

The physical and command watchdogs remain200ms. A physical publication up to25ms newer than a caller's QPC is tolerated, because another callback can publish after that caller samples time; its reported physical age clamps to0. Larger future timestamps fail closed. Hook callers resample QPC after IPC reads, reducing stale caller-clock windows. The same-epoch anchor remains intact across genuine watchdog fallback and recovery.

Input diagnostics extend the same status block: offset 224 `inputCoverage` (u32), offset 228 `selectedMenuPath` (u32), offset 232 `menuRisingEdges` (u64), and offsets 240/244/248/252 `menuPressed`, `lastInputError`, `effectiveNativeActions`, `inputArmed` (u32 each). Coverage bits are 1 left X scalar, 2 left Y scalar, 4 right trigger click/value, 8 right grip/squeeze click/value/force, 16 selected Boolean menu click, 32 right A Boolean click, 64 left stick Boolean click, and 128 HMD proximity Boolean. These report captured components with matching kinds, not active application bindings or human behavior. Menu paths are 0 none, 1 left Y, 2 left B, 3 right B, and 4 left application-menu.

Menu state and rising-edge count advance only after the original input backend accepts the selected synthetic Boolean write. A rejected press does not claim delivery. The last nonzero Boolean/scalar `EVRInputError` is retained until this driver instance restarts; a later successful write does not erase that diagnostic. Effective native actions and armed state describe a valid committed desktop request, and are zero during physical fallback or disarm. They describe requested action ownership; accepted menu output is reported separately. Older brokers can ignore this additive extension.

Additive source telemetry occupies offsets256 `proximityKnown` (u32),260 `proximityActive` (u32),264 `leftPhysicalAgeMilliseconds` (double),272 `rightPhysicalAgeMilliseconds` (double), and280 `proximityAgeMilliseconds` (double). Proximity is the last original vendor Boolean before synthetic routing, published with its QPC in one atomic word. Creation alone and synthetic worn=true never establish source state. Recreating a component resets observation; conflicting reused identity, multiple selected HMD proximity components, or hook-integrity failure reports unknown. Vendors may publish proximity only when it changes, so event age is informative and can exceed200ms while known remains true. A consumer must separately require fresh independent head capture. This is vendor proximity evidence, not a guarantee that a particular transport exposes a physical wear sensor. Ages are-1 when absent/invalid; controller ages derive from independent original pose callbacks and do not redefine the older `hasLeft`/`hasRight` fields.

Error values: 0 none, 1 missing/invalid head, 2 stale physical source, 3 stale broker command, 4 malformed/future command or readable invalid startup schema, 5 conflicting hook, 6 runtime/interface gate, 7 opt-in disabled, 8 IPC unavailable, 9 missing captured controller components, 10 startup configuration resolution/read/size failure.

## Build and isolated evidence

```powershell
cmake -S . -B build/native -G "Visual Studio 17 2022" -A x64
cmake --build build/native --config Release -j 8
ctest --test-dir build/native -C Release --output-on-failure
```

The driver is at `build/native/driver/switcheroonie/bin/win64/driver_switcheroonie.dll`; diagnostics and tests are in `build/native/Release`. Runtime registration is intentionally a separate operation.

`switcheroonie-native-tests` checks routing, 100 switches, independent physical storage, malformed/stale/future IPC, disarm/focus semantics, tracker exclusion, and concurrent capture/input/pose/status calls. `switcheroonie-hook-tests` uses actual MinHook method interposition in its own isolated fake-host process and checks independent physical movement, synthetic head/input, tracker/system/proximity isolation, clean physical reacquisition, 100 switches, a broker-loss deadline, hook removal, and pre-existing-hook refusal. These tests never load a SteamVR scene or prove real F1-F5.

Configuration fixtures cover missing and deliberately wrong environment values, real Win32 open/lock errors, BOM input, oversize and malformed files, and fail-closed empty input. The host fixture has distinct companion/HMD/left/right/tracker contexts and rejects cross-provider writes. It verifies Tick-only pose/actions use each vendor context, synthetic proximity does not contaminate raw false source, and recreated/conflicting proximity identities become unknown.

`isolated-foreign-calibration-chain` loads a separate fixture DLL with its own separately linked MinHook library. It checks the same bounded trampoline resolver, independent raw/calibrated/captured/output streams, 25 switches, tracker transforms, input synthesis, restoration of the foreign pipeline on own removal, and concurrent Cleanup while a raw foreign call is held before entering the inner trampoline. New calls are gated during that drain, and the test ends with the intentional retained shutdown gate. This fixture establishes hook ordering and lifetime behavior in an isolated process; it is not execution of the installed SpaceCalibrator DLL or a hardware calibration test. `packaged-driver-resources` verifies the copied manifest name and owned load-priority resource path/value.

`switcheroonie-diagnostics [--ipc] [--output file.json]` is read-only. It initializes OpenVR as `VRApplication_Background` only if `vrserver.exe` already exists; otherwise it reports that probing was skipped. Device serials are hashed with a user-specific salt. Diagnostic client poses are explicitly post-routing and cannot prove F1. The controlled scene must be explicitly launched by the user during a hardware test window.

For the actual independent-source experiment, run `switcheroonie-diagnostics --record physical-output.jsonl --seconds 15 --hz 30` while SteamVR, this opted-in driver, and a controlled scene are already active. Bounds are 1–60 seconds and 1–120 Hz. The JSONL records QPC timing, exact SDK revision/runtime build, client head pose in `TrackingUniverseStanding` with zero prediction, and the driver's captured pre-output head pose with validity/heartbeat/hook flags, counters, mode, and transaction epoch. It contains no raw serials or scene identifiers. Driver coordinates may exclude the client's standing/chaperone transform, so compare independent changes before assuming absolute positions match. Move only the physical HMD while synthetic look is held, then hold the HMD while mouse look changes; record both distinct streams and observe stereo output. A generated capture file alone is not a passed F1 test. Recording refuses to start without an existing runtime and stops if that runtime disappears or changes process identity.
