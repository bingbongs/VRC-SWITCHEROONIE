# Optional owned OpenVR → VDXR graphics bridge

Status: **the isolated normal-graphics probe is implemented and validated offline; the graphics bridge remains proposed, with no live normal-graphics test yet**. This is the next concrete candidate after the installed VD shim failed both persistent-HMD trials. It must stay outside the normal package and cannot activate automatically in an existing runtime. See [the graphics probe](../research/vd-graphics-probe/README.md).

## What the experiments established

The owned persistent HMD started an absent-headset SteamVR scene, but both accepted eye submissions did not establish compositor presentation: prediction ID stayed 2. The VD display provider failed initialization without a client; reconnecting did not provide usable VR. A connected-start trial loaded VD's server driver but showed Headset Error(-202), with only the VD desktop visible. A compositor module-name filter returned no matching names during both this failure and a successful normal VD recovery, so it cannot establish compositor absence or transport ownership. See [late attachment](../reports/persistent-hmd-absent-late-attachment-result.json) and [connected start](../reports/persistent-hmd-connected-result.json).

The separate headless session also failed physical-source qualification: 299 identical poses and inactive controller actions accompanied measurable motion in the normal vendor source. Its short coexistence observation passed only scene continuity. See [the motion result](../reports/vd-headless-motion-result.json). None of these results proves headset-free VRChat continuity or a VD-compatible persistent display.

A direct public LibOVR invisible-session test likewise returned 150 samples with sensor time 0, tracking flags 0, identity head pose and unavailable controllers. Successful SDK calls and true mounted/visible/focus fields did not qualify a source. See [the direct result](../reports/vd-public-libovr-result.json). The normal graphics candidate must therefore establish actual motion and headset delivery, not infer them from SDK status.

## Public implementation route

Keep one owned HMD resident for the runtime lifetime, and add one owned `TrackedDeviceClass_DisplayRedirect` exposing `IVRVirtualDisplay_002`. Its manifest uses `redirectsDisplay=true`. `Present` receives the final compositor shared texture, frame ID and vsync information; it must queue work promptly. `WaitForPresent` and `GetTimeSinceLastVsync` supply display timing. This is the documented wireless-display access point, distinct from the current desktop/debug placeholder. [Pinned Valve driver API](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/docs/Driver_API_Documentation.md#ivrvirtualdisplay), [pinned header](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr_driver.h).

A separate owned process creates a **normal graphics** OpenXR session through the already pinned VDXR runtime, selected by process-local `XR_RUNTIME_JSON`. It enables `XR_KHR_D3D11_enable`, without `XR_MND_headless`. Query `xrGetD3D11GraphicsRequirementsKHR` before session creation; create the D3D11 device on the returned adapter LUID at the required feature level, then pass `XrGraphicsBindingD3D11KHR`. Enumerated swapchain images are runtime-owned D3D11 textures. [Khronos D3D11 binding](https://github.com/KhronosGroup/OpenXR-Docs/blob/main/specification/sources/chapters/extensions/khr/khr_d3d11_enable.adoc).

The published VDXR implementation distinguishes graphics-bound sessions from headless sessions and creates its normal vendor session for graphics. This makes the route implementable through public APIs, but does not prove the installed binary can coexist with or replace the SteamVR stream. Retain the loader/runtime pinning, medium-integrity requirement, layer isolation, bounded telemetry and external owned-process timeout of [the headless probe](../research/vd-headless-probe/README.md). [Pinned VDXR session implementation](https://github.com/mbucchia/VirtualDesktop-OpenXR/blob/1a83fec8b5c565b14b06ffa8e1eb7e4768057573/virtualdesktop-openxr/session.cpp).

## First candidate and admission gates

1. Build an isolated `vd-graphics-probe`: default help/file validation performs no vendor loading; explicit graphics mode draws a distinct left/right grid and moving frame counter for a bounded interval. Use `xrWaitFrame`, `xrBeginFrame`, predicted-time `xrLocateViews`, acquire/wait/release swapchain images, and `xrEndFrame`. Record session events, view/action activity, query/predicted times, submission results and masked motion metrics. No SteamVR textures or Broker bridge in this first test.
2. In a stopped-runtime experiment, journal a reversible public configuration override disabling the competing **VD SteamVR provider only**, while keeping Streamer/VDXR available. This is a future controlled change, not performed by this design. Verify effective provider enablement/registration and runtime admission evidence; module-name substring matching alone does not prove display ownership. Refuse ambiguous dual display ownership. Never edit vendor files or intercept its private transport. Keep unrelated drivers/calibration settings exact. The current research manager does not implement this override.
3. With the owned SteamVR HMD/scene alive, run the normal graphics probe and deliberately move head/controllers. Require actual stereo delivery, changing independent samples and continued SteamVR process identity. Test disconnect → reconnect separately. A failure here stops admission to the texture bridge.
4. Only after that passes, add the owned DisplayRedirect frame bridge, then qualify desktop hold and physical return in the controlled scene. VRChat same-process continuity is a later test.

## GPU ownership and timing

Use the same adapter for the owned HMD/compositor copy device and the XR device. The current high-performance-adapter guess is insufficient; qualify and retain the reviewed VDXR LUID for absent starts, and refuse a mismatch. Inspect every source texture's dimensions/format/sample count; `PresentInfo_t` supplies no eye rectangles. Establish the compositor atlas from the owned display geometry and test eye order rather than assuming two equal halves.

`Present` opens/caches the compositor's legacy shared texture and queues a copy into an owned two/three-slot GPU ring. The compositor may reuse its buffer, so the ring needs explicit completion and reuse ownership. Valve's sample demonstrates shared-texture consumption, but uses an older interface and blocking completion technique; it is a starting reference, not a drop-in implementation. [Valve virtual-display sample](https://github.com/ValveSoftware/virtual_display/blob/master/driver_virtual_display/driver_virtual_display.cpp).

Export only owned ring textures to the exact helper process. Distinguish legacy shared handles from NT handles; do not blindly duplicate the incoming compositor handle. Validate format/copy compatibility, flush writes when required, and use bounded synchronization. A keyed-mutex timeout drops the frame; abandonment recreates owned resources. No infinite acquire, CPU readback or OpenXR/vendor call belongs inside `Present`. [Microsoft shared resources](https://learn.microsoft.com/en-us/windows/win32/api/d3d11/nf-d3d11-id3d11device-opensharedresource), [keyed mutex outcomes](https://learn.microsoft.com/en-us/windows/win32/api/dxgi/nf-dxgi-idxgikeyedmutex-acquiresync).

The helper copies/blits the newest completed atlas regions into acquired XR images, including explicit color-space conversion where needed. Bound the IPC/ring queue and drop stale frames. Provide an advancing synthetic virtual-vsync clock while absent; when connected, relate XR predicted time and submission receipt to QPC. Keep synthetic clock, queued frames and real XR submissions separate in telemetry. `WaitForPresent` gets a finite local deadline so helper loss cannot freeze the compositor.

## Camera, optics and independent source

Use XR view configuration sizes/FOV and per-eye transforms to replace placeholder optics. The pinned OpenVR host exposes `SetDisplayProjectionRaw`, `SetDisplayEyeToHead` and `SetRecommendedRenderTargetSize`; coordinate geometry-generation changes with frame allocation. Match reference spaces and recenter events explicitly. An existing VRChat process may not accept arbitrary resolution/projection changes correctly; measure this rather than claiming dynamic optics support. [Pinned host interfaces](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/headers/openvr_driver.h).

Physical mode needs render-pose/time correspondence between SteamVR's final image and the XR projection layer. Re-submitting an already composited/timewarped image risks double reprojection. Desktop mode also cannot attach a frozen image to a physical world-space pose and assume it stays fixed. OpenXR composition uses the layer's declared space/pose. [Khronos rendering semantics](https://github.com/KhronosGroup/OpenXR-Docs/blob/main/specification/sources/chapters/rendering.adoc).

A concrete desktop experiment is two eye-specific VIEW-space quad layers: the published VDXR implementation maps these to headlocked vendor quads and supports eye selection in its VD backend. This could preserve a stereo panel while the physical head moves; it is not equivalent to a full-FOV projection and its optics/comfort require human testing. The installed behavior remains unverified. [Pinned VDXR quad handling](https://github.com/mbucchia/VirtualDesktop-OpenXR/blob/1a83fec8b5c565b14b06ffa8e1eb7e4768057573/virtualdesktop-openxr/frame.cpp).

Publish raw head/controller samples from the independent XR helper, never from the already routed SteamVR HMD. A proposed `RawSourceSnapshot` includes helper/session/reference-space generations, QPC receipt, requested/predicted XrTime, API flags, head/grip/aim poses and active actions. Flag validity alone is insufficient after the failed headless test. Qualification needs deliberate motion and actual delivery; ongoing stillness must not be mistaken for disconnection. FOCUSED does not prove worn status.

## Contracts, recovery and required proof

Add separate research contracts for `LogicalDisplayReady` (owned Present/vsync advancing), `PhysicalSourceReady` (qualified independent source with fresh lease), `TransportReady` (XR submission plus separately recorded headset presentation), and acknowledged route epoch. The current Broker requires a physical source and cannot drive this cold synthetic HMD; these are future additive interfaces, not a status relabel.

The supervisor retries absent XR system/session creation with bounded backoff. Helper death/session loss releases only owned XR/GPU objects, invalidates physical actions, and leaves the same HMD alive with synthetic controls. Current-user-only IPC carries explicit protocol/generation/slot ownership and never raw text/device identifiers. Admit the product only after absent startup, stereo mouse look, deliberate tracking, connect/disconnect/reconnect, helper death, recenter and unchanged VRChat/runtime identities pass. Preserve FBT/controller calibration and focus/audio behavior as separate checks. Long-duration and general-use reliability remain separate unperformed tests.
