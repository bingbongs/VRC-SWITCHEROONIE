# Compatibility and evidence

Connected switching remains **experimental**. Earlier controlled-scene checks passed stereo presentation, switching, held-view stability and physical return; later VRChat checks exposed controls problems. The signed 0.2.2 driver disconnects and invalidates all ten Virtual Desktop generic trackers in Desktop, verified through an independent OpenVR client. VRChat's enabled Freeze Tracking on Disconnect initially kept the body pose. After disabling it inside VRChat, the user confirmed Desktop body movement/posture and return to full-body tracking. Cursor hiding, mouse-look lag, wrist aiming and persistent VRChat locomotion animation still failed. These route-specific results do not establish universal headset or FBT compatibility.

OpenVR defines `GenericTracker` as a shared tracker class, with tracker roles assigned separately. This permits a common routing rule for devices presented through that interface, but does not prove a particular vendor's source timing, calibration, hook coexistence or display behavior. [Valve's pinned tracker API documentation](https://github.com/ValveSoftware/openvr/blob/0924064316de3effbcd1acf1e309182a2deb1c05/docs/Driver_API_Documentation.md#trackers-full-body-tracking).

VRChat's public OSC tracker API accepts position/rotation vectors and optional head alignment data, and documents a normal ten-second data timeout. It does not document a per-tracker enabled/valid endpoint. Stopping a cooperating sender would therefore not establish an immediate 200 ms release, and sending a zero position is a pose update rather than a disable command. **Inference:** a SteamVR pose router cannot suspend or rotate a separate OSC stream delivered directly to VRChat; that requires a separately owned data path. [VRChat OSC Trackers](https://docs.vrchat.com/docs/osc-trackers).

SteamVR installation build `25330290` is gated in this experimental binary. Software simulation establishes routing logic on a fake host; it does not establish compatibility with any physical provider on that build. Store exact runtime/application/headset/firmware/transport/controller/GPU/add-on versions with every future hardware result.

The existing application monitor is the viewer. Correct physical eye presentation, projection, tracking latency and display-owner continuity must be verified in the HMD. The panel deliberately leaves display readiness unverified rather than inferring it from a pose heartbeat.

Live setup on 2026-10-07: early SteamVR starts skipped the owned LocalAppData directory even though the same user's Win32 directory checks succeeded. An owned installation outside AppData/OneDrive, with the optional manifest directory field omitted and owned load-priority setting added, loaded successfully; which change resolved discovery is unproven. No ACLs were widened. The exact approved SpaceCalibrator path now routes after independent physical calibration capture, with live pose and component evidence; FBT calibration behavior remains untested. Controlled-scene texture submission error 106 was repaired, then the separate anchor timing race was repaired and retested. Original failures remain preserved. The old desktop VRChat process ended during setup; later starts are not continuity evidence.

The persistent-HMD trials reached synthetic scene submission but failed actual Virtual Desktop headset delivery and were rolled back. Headless OpenXR and invisible LibOVR also failed physical-source qualification. The optional normal-graphics OpenXR probe is built and tested offline; it has not established a live source or headset-free session.
