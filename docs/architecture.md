# Architecture

The panel and recovery CLI use a versioned named pipe restricted to the current Windows user. The broker owns transactions, focus checks, input leases and configuration. It survives panel closure; the panel is not the pose loop. Broker status separates requested/committed source, physical tracking freshness, input ownership and unverified display readiness.

The primary input owner is the clicked foreground VRChat game window. A pure ownership state machine consumes the acquisition click, gates keys held at acquisition until released, and routes relative mouse look and movement. M or Esc toggles the same Quick Menu state and persistent raised left hand; Tab passes through unchanged. Menu navigation suppresses locomotion and holds the head steady. Holding right mouse outside the menu temporarily routes motion to the pointer without pressing Grip; middle mouse holds grab. C/Z toggle mutually exclusive crouch/prone; a second press returns to standing. Chat entry and focus loss release input. The Windows adapter uses a separate Raw Input message thread; its scoped keyboard hook handles only control-key edges. Look mode recenters an owned bounded cursor clip and uses a one-pixel non-activating cursor surface to hide the Windows cursor; pointer mode confines it to the validated game client. Cursor confinement requires an independent helper heartbeat and a bounded ownership lease. The optional pad has a separate HWND-scoped lease; late pad teardown or stale updates cannot cancel game ownership. Global release always clears every owner and requires a fresh game click. These controls remain a software-tested candidate after the previous live F3 failure.

Menu pulses are broker-owned, last180ms, and have a60ms neutral interval between queued presses. A panel timer or blocked UI pipe no longer determines delivery. The native layer selects one verified Boolean menu click component and keeps touch channels neutral. Accepted backend menu edges, coverage, selected path, and input errors are reported independently; those counters do not prove that the game consumed the action.

The native user-mode SteamVR server driver preserves the vendor HMD and display/compositor components. The experimental backend captures `IVRDriverInput_004` components during startup and defers pose ownership validation while companion drivers initialize. It routes an unpatched `IVRServerDriverHost_006` method directly, or the original pose trampoline of one exact approved SpaceCalibrator binary. The latter receives calibrated physical poses after SpaceCalibrator's independent physical feed is stored; generated output bypasses that calibration path. HMD/controller identities persist, and calibrated tracker poses pass through. Unknown patch chains are refused. Raw, calibrated, captured, and output boundaries have isolated tests; actual FBT behavior remains a hardware check.

The driver gates the process runtime installation, executable targets, interface revisions, installed appmanifest build `25330290` and explicit `driver.json` opt-in. That pin is an experimental compatibility guard, not a claim of official API stability or vendor approval. No code is loaded into VRChat or another scene app.

The data plane is one 4096-byte, SID-restricted Windows shared-memory mapping. Broker request block starts at 0, driver status at 2048, and OSC watchdog timestamp is at 3080. Each block uses aligned atomic 64-bit words, bounded sequence checks and independent QPC timestamps. Broker request payload through offset 96 matches `native/protocol.hpp`; offsets 104–128 add OSC enable/port/axes/actions and are ignored by native routing. Offset 60 in status contains native mapping capability flags. No realtime callback waits for IPC, UI, disk, or network.

Additive native status offsets224–252 report exact component coverage, the selected menu path, accepted synthetic menu rising edges and level, sticky backend input error, effective action bits and armed state. Old driver builds leave these zero. Cursor ownership uses a separate uniquely named SID-restricted map and cannot alter pose or OSC requests.

Mode changes neutralize owned input, advance an epoch, prepare the destination, and await actual driver epoch/mode acknowledgement. A timeout returns rejection and retains the last observed source. Rapid requests serialize; repeated request IDs return their prior result. The physical-return check requires a fresh independent source, with no restart or instance rejoin operation.

The resident service starts with no runtime/headset and retains manual intent before waiting for the native transaction gate. Pending duplicate IDs share one transaction. Every publication/acknowledgement/timeout boundary checks the current intent generation; newer manual/Auto configuration supersedes obsolete work and neutralizes input. Manual preferences queue until healthy tracking becomes available. Startup adopts an existing healthy route, epoch and bounded pose settings with all input released, preserving the immutable native head anchor. It does not treat a saved preference or a service response as a committed mode.

Automatic selection reads observed original vendor HMD proximity separately from the synthetic awake signal. One unambiguous physical component and fresh independently captured head poses are required; source events may be change-only and retain an honest age. Wear/removal dwell times are750/1000ms, failures retry with backoff, and manual choices remain in force until Auto resumes. A mode change never arms mouse/keyboard capture. Unknown wear semantics retain the current route and require manual selection until measured for that transport.

The WPF panel remains in the tray when closed, reconnects or restarts its owned broker with bounded backoff, and has an optional per-user Windows sign-in entry. Neither UI startup nor service retry launches/restarts VRChat or SteamVR. A service stop releases input; callback/IPC lifetime is independent of panel visibility. Actual crash/cursor/transport behavior still needs live evidence.

Desktop head yaw/pitch is anchored once at entry, leveled to the horizon, bounded and expressed in meters/radians. A desktop-only Y offset never changes floor calibration. Resting hands are used for ordinary look and disarmed output; pointer mode moves the right hand near the view while keeping the left near the body. Crouch/prone adjust synthetic head height from the immutable anchor without accumulating offsets; captured world Y is not proof of the user's standing floor. Locomotion uses left controller axes or optional OSC, never room-scale HMD translation. Disarming releases buttons/axes while keeping the desktop head pose selected as long as the broker lease is fresh.

The native 200ms deadline falls back to physical passthrough on broker failure. A separate OSC process owns send-only movement packets and releases on stale leases; the broker also emits emergency neutral packets when the helper fails. Neutral packets repeat for a bounded 250ms window to reduce UDP-loss risk. If every OSC sender dies or the receiving route drops packets throughout the release window, release cannot be guaranteed; the documented recovery sender is needed.

Application profiles declare the shipped bindings and limits. The native core is application-independent, but its provisional button-path mappings are not a universal action system. Stored Oculus/PICO binding evidence informed the VRChat profile. Actual controller identity, menu selection, haptics, skeleton channels and FBT calibration remain separate validation tracks.

Scenario C requires a display owner that survives absence and later routes stereo textures to the requested transport. The connected backend owns no display adapter. The separate persistent-HMD provider admitted one synthetic HMD, but both absent-client late attachment and connected-start Virtual Desktop display failed; its registration was rolled back. Public headless OpenXR and invisible LibOVR did not qualify as independent physical sources. A separately built normal-graphics OpenXR probe is the next research candidate before any owned OpenVR display-to-OpenXR bridge. Its live display/source behavior and the bridge remain unproven; the resident service's ready state is distinct. See the cold-start decision and `headset-free-startup-design.md`.


## Optional body rotation

speeeeeeen is disabled by default. Only its preference is saved. An explicit Numpad5 press in the foreground VRChat window activates a separate lease in either routing mode. Numpad4/6 adds lateral roll, Numpad8/2 adds pitch; speed ramps up, coasts on release and brakes faster with the opposite key. Typing, focus loss, emergency release, mode changes and stale tracking remove authority.

The broker publishes a normalized quaternion and fixed body pivot based on the original physical head. The driver composes the same WORLD rigid transform onto the head, controllers and generic trackers while retaining original captures. Tracking references are excluded. This is tracked-device rotation, with actual avatar/FBT IK behavior requiring a live test.

The Windows cursor surface handles WM_SETCURSOR for an app-owned one-pixel window at the existing look lock. It uses WS_EX_NOACTIVATE, never changes the global cursor theme, and never patches another window's procedure or cursor counter. It disappears in pointer mode, on stale authority and on process exit. [Microsoft cursor documentation](https://learn.microsoft.com/en-us/windows/win32/menurc/wm-setcursor)
